## Pre-registration (PART 0.6–0.9)

Written and committed before any forecast, skill, direction test or weight was computed. Not to be
edited after results exist.

### Common definitions
- **Times.** T* = 2026-10-03 16:00 UTC. H = the holdout start in `validation/validation_set_v1.json`
  (T* − 56 days = 2026-08-08 16:00 UTC).
- **Pool.** The validation pool for CORE: windows starting at 16:00 UTC on or after 2020-06-01, lasting
  14 days, ending at or before H, with all CORE features defined.
- **Outcomes** come from the validation outcome table:
  - Y1: BTC 14-day log return
  - Y2: BTC hourly realised volatility
  - Y5: cross-sectional dispersion
  - Y8: BTC max rebound
- **Age of window w:** age_w = days from its end (t0_w + 14 d) to T*. In the walk-forward, to the test
  date D instead.
- **Test dates D:** every 7 days from 2022-07-01 16:00 UTC up to H − 14 days. SCREEN = D ≤ 2024-06-30;
  CONFIRM = D ≥ 2024-07-01. At each D only pool_D = {pool windows with t0 + 14 d ≤ D} is used.
- **Percentiles.** Percentile space means mid-rank percentiles within a reference pool: (#less + ½·#equal)/n.
  The reference pool is pool_D in the walk-forward and the full pool at T*. An observed value at D is
  mapped with pool_D.
- **Intervals:** moving-block bootstrap over consecutive test dates, blocks of 4, 2,000 resamples,
  seed 20261003, 5th–95th percentiles.

### Weighted fair CRPS (used everywhere below)
- For members x_i with weights w_i ≥ 0 and Σw = 1 (identical windows merged by summing their weights):
  - `CRPS_fair(x, w; y) = Σ_i w_i |x_i − y| − ½ · Σ_{i≠j} w_i w_j |x_i − x_j| / (1 − Σ_i w_i²)`
  - The second term is 0 when a single member holds all the weight.
- With equal weights it equals the unweighted fair CRPS, mean|x − y| − Σ_{i,j}|x_i − x_j| / (2n(n − 1)).
  A unit test checks this.
- **Kernel version** (bandwidth choice, percentile space). Each member is a Gaussian N(u_i, b²):
  - `CRPS_fair_b(u, w; v) = Σ_i w_i A(u_i − v, b²) − ½ · Σ_{i≠j} w_i w_j A(u_i − u_j, 2b²) / (1 − Σ w_i²)`
  - A(μ, s²) = E|μ + sZ| = 2s·φ(μ/s) + μ·(2Φ(μ/s) − 1).
  - As b → 0 it equals CRPS_fair. There is no boundary correction at 0 and 1.
- **Skill** of a forecast c for outcome Y over a period = 1 − Σ_D CRPS(c) / Σ_D CRPS(whole pool, equal
  weights). Mean skill = the mean of the Y2, Y5 and Y8 skills.

### 0.6 Forecast ensemble for Y2, Y5, Y8 (Y1 and Y6 are not forecast)
- **Candidates at each D:**
  - (a) `LOOK`: the 25 CORE lookalikes for the state at D, picked exactly as in the validation
    (percentiles on pool_D, the same distance and the same spacing rules), equal weights.
  - (b) `REC_HL`: all of pool_D weighted ∝ 0.5^(age/HL), for HL ∈ {60, 120, 180, 365, 730 days, ∞}.
    HL = ∞ is equal weights, i.e. the whole pool.
  - (c) `MIX`: 0.5 × LOOK + 0.5 × REC_HL*, where HL* is the (b) half-life with the best SCREEN mean skill
    (ties go to the earlier HL in the list above).
- **Test dates used:** only dates where LOOK can pick 25 windows, so every candidate is scored on the
  same dates.
- **Scoring:** CRPS_fair in raw units, separately for Y2, Y5 and Y8.
- **Rule:** choose the candidate with the best SCREEN mean skill (ties in the order a, b60, b120, b180,
  b365, b730, b∞, c). Keep it only if its CONFIRM mean skill is > 0, i.e. it beats the whole pool.
  Otherwise use (a).
- **Bandwidth:** b ∈ {0.05, 0.10, 0.15, 0.20}, default 0.10.
  - Score: the chosen ensemble's kernel CRPS_fair_b in percentile space, per Y. Baseline: the whole
    pool's CRPS_fair in percentile space.
  - Choose the best SCREEN mean skill (ties → smaller b). Keep it only if its CONFIRM mean skill is > 0;
    otherwise b = 0.10.
- **Forecast at T*:** the chosen ensemble on the full pool (LOOK = the 25 windows in the validation
  artifact for the same as-of; ages measured to T*) with the chosen b.
  - Report per Y the forecast median and the 10th and 90th percentiles of the marginal mixture, in
    percentile space and in Y units.
  - Y units come from the pool's empirical quantile function: linear between sorted values at
    (k − ½)/n, clipped to the observed range.

### 0.7 Direction mix: tested before use
- **Trend state at t:** (tercile of T2, sign of T1), with T1 = BTC 30-day and T2 = BTC 90-day log
  return, exactly as in the validation features.
  - Tercile cut points: the 1/3 and 2/3 quantiles (numpy "linear") of T2 over the reference pool.
  - Sign: "up" if T1 > 0, else "down".
- **p_up(state)** = the share of reference-pool windows in that state with Y1 > 0. If fewer than 30
  windows share the state, use all windows with the same tercile and say so.
- **Baseline:** the unconditional share of reference-pool windows with Y1 > 0.
- **Test:** at every weekly D (pool_D as the reference), Brier score (p − o)², where o = 1 if Y1 at D > 0.
  Brier skill = 1 − Σ Brier(p_up) / Σ Brier(baseline) per period.
- **Rule:** use p_up only if its Brier skill is > 0 in BOTH SCREEN and CONFIRM. Otherwise apply no
  direction reweighting.
- **Reported at T* in either case,** with the verdict: p_up for T*'s state, the number of windows behind
  it, and a 90% interval from a moving-block bootstrap over that state's windows in start order (blocks
  of 14 consecutive windows, 2,000 resamples).

### 0.8 Event calendar (for a proposed view field only; NOT used in the weights)
- **What:** US CPI release times and FOMC-minutes release times, 2020-01-01 → 2026-12-31.
- **Sources:** the official Bureau of Labor Statistics CPI release schedules and the Federal Reserve FOMC

- **Times:** local America/New_York times converted to UTC.
- **Storage:** `validation/event_calendar_v1.csv`, with the source URL of every row.

- **Unreachable source:** report it and leave those rows out. Never approximate.

### 0.9 Live-like weights (no CPI filter)
- **Base weight:** for every pool window w, base_w = the chosen ensemble's product-Gaussian kernel density
  (bandwidth b, ensemble weights ω_i, 3 dimensions) evaluated at w's realised (Y2, Y5, Y8) percentiles
  within the full pool:
  - `f(u) = Σ_i ω_i Π_d φ((u_d − u_i,d)/b) / b`
- **Direction factor, only if 0.7 passes:** rescale base weights within "BTC up" windows (Y1 > 0) to sum
  to p_up, and within the others to sum to 1 − p_up. Otherwise normalise all to sum to 1.
- **Report:** the effective number of windows (Σw)²/Σw², and the 25 highest-weight windows picked
  greedily in weight order with starts ≥ 14 days apart (used by `--quick` later).
- **Output:** `validation/live_like_v1.json`, with the as-of, the rules, grids and skill tables, the
  forecast, the direction test, the events, every window's weight, the git commit, input hashes and the
  artifact's own sha256.
- **Oct 3 rerun:** `python -m src.validation.live_like --asof "2026-10-03 16:00"`, after the validation
  build with the same `--asof`.
